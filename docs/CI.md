# CI 운영

PR에서는 변경 내용을 검사하고, main의 앱 릴리스에서만 배포합니다. 테스트와 배포는 별도 작업입니다. `PR policy`는 제목과 출발 브랜치만 확인하는 짧은 검사입니다.

## 언제 무엇을 실행하나요?

| 변경·이벤트                                                        | 실행                                                 |
| ------------------------------------------------------------------ | ---------------------------------------------------- |
| README·문서·스토어 소개·신고 양식만 변경                           | 포맷 검사, 브라우저 검사 생략                        |
| 단위 검사만 변경                                                   | 정적·단위·배포 계약 검사와 빌드                      |
| 특정 합성 E2E 파일 또는 팝업 화면만 변경                           | 위 검사와 해당 브라우저 검사                         |
| 엔진·저장소·공통 UI·자원·의존성·권한·빌드·CI 또는 미분류 파일 변경 | 정적 검사·빌드·전체 MV3                              |
| develop push                                                       | 실행하지 않음. 병합 전 PR 검사 사용                  |
| 앱 릴리스 PR 및 main push                                          | 전체 MV3 성공 근거 확인, 현재 커밋에서 ZIP 빌드·검증 |
| 수동 `verify`                                                      | 재사용 없이 전체 검사                                |
| 수동 `release`                                                     | 같은 입력의 성공 기록이 있으면 Windows 검사 재사용   |
| 수동 `store-status`                                                | 스토어 상태 조회만 수행                              |

문서의 링크·설명·명령이 실제 동작과 맞는지는 리뷰에서 확인합니다. 포맷 성공만으로 문서 내용의 정확성을 보장하지 않습니다. 자동 선택은 `scripts/ci-contract.mjs`의 제한적인 목록을 사용하며 모르는 경로는 전체 검사로 처리합니다.

Windows MV3는 독립 프로필 두 개로 병렬 실행합니다. CI에서는 첫 실패가 나오면 남은 실행을 중단하고, 자동 재시도는 하지 않습니다. 마지막 실패 이후 실행되지 않은 검사는 통과로 기록하지 않습니다.

## 전체 검사 결과 재사용

`Verification plan`의 Actions 요약에서 새 실행인지 재사용인지, 재사용한 실행 링크를 확인할 수 있습니다. 다음 조건을 모두 만족해야 합니다.

- 같은 저장소의 `ci.yml` 실행이 최근 24시간 안에 성공했습니다. 포크의 실행은 사용하지 않습니다.
- Git tree의 파일 경로·파일 모드·내용 해시가 같습니다. 명시한 문서 경로만 비교에서 제외합니다. 코드·테스트·의존성·도구 설정·워크플로는 모두 비교합니다.
- 그 실행의 현재 시도에서 정적 검사와 실제 Windows 전체 MV3 실행이 성공했습니다. 일부 검사, 생략, 실패 또는 다른 실행에서 재사용한 결과는 근거가 되지 않습니다.
- GitHub 조회가 성공하고 전체 tree를 확인할 수 있습니다. 조회 오류·기록 만료·입력 차이가 있으면 필요한 검사를 새로 실행합니다.

PR은 표시된 head SHA를 검사합니다. 두 브랜치의 필수 검사에는 최신 base 반영을 요구하는 보호 규칙을 유지합니다. base가 바뀌면 먼저 PR을 갱신하고 다시 검사해야 합니다. `MV3 (Windows)` 필수 게이트는 계획 실패나 실제 MV3 실패를 성공으로 처리하지 않습니다.

배포 ZIP은 재사용하지 않고 현재 커밋에서 다시 빌드합니다. CI·문서만 main에 반영할 때는 버전과 배포 입력이 바뀌지 않으므로 릴리스·심사 제출을 실행하지 않습니다. 스토어 제출은 동시에 하나만 허용하며 진행 중인 심사를 교체하지 않습니다.

브라우저 검사 재사용으로 실제 실행 단계가 생략되어도, 필수 `MV3 (Windows)` 확인이 성공하면 후속 릴리스를 진행합니다. 정적 검사나 필수 확인이 실패·취소·생략된 경우에는 배포하지 않습니다.

## 실패를 조사하는 순서

1. 실패한 테스트 이름과 `.output/qa/results/summary.json`의 오류를 확인합니다. 본문 준비 대기, 기대값, 제품 동작, 브라우저 종료 오류를 구별합니다.
2. 필요하면 실패 폴더의 `trace.zip`을 `pnpm exec playwright show-trace 경로`로 엽니다. 테스트가 준비 완료 전에 조작했는지도 확인합니다.
3. 빌드가 바뀌었다면 `pnpm run build:e2e` 후 해당 `.spec.ts`만 실행합니다. 같은 빌드의 직전 실패만 다시 볼 때는 `pnpm exec playwright test --last-failed --workers=1`을 사용할 수 있습니다.
4. 원인 수정 후 관련 검사부터 확인합니다. CI 설정·공통 런타임 변경 등 전체 회귀가 필요한 경우에만 범위를 넓힙니다. 우연히 통과할 때까지 전체 실행을 반복하지 않습니다.

일반 결과는 다음 실행에서 갱신됩니다. 실패 사본은 `.output/qa/failures/run-*`에 남고, 정상 종료한 임시 프로필은 삭제합니다. 실행이 강제 종료되면 프로필이 남을 수 있습니다. GitHub 실패 산출물은 3일, 배포 준비 ZIP은 7일간 보관합니다.

```sh
# 중단된 프로필·실패 사본 중 7일이 지난 정리 대상을 확인합니다.
pnpm run qa:clean
# 표시된 대상만 삭제합니다.
pnpm run qa:clean --apply
```

이 명령은 이 프로젝트의 표식이 있는 실행 폴더만 처리합니다. 실행 중인 프로세스, 다른 프로젝트, 운영체제 Temp 전체, 설치된 브라우저 프로필은 삭제하지 않습니다. 자동 주기 작업은 만들지 않으므로 필요할 때 실행하세요. QA 결과는 Git에서 제외됩니다.

## Dependabot 사용

매주 월요일 한국 시간 02시에 호환 가능한 minor·patch 업데이트를 런타임, 개발 도구, GitHub Actions 묶음으로 제안합니다. 주요 버전은 호환성 검토가 필요한 별도 PR로 남기며 Node 타입·TypeScript의 기존 주요 버전 제한을 유지합니다. 보안 업데이트는 정기 버전 묶음과 별개입니다.

봇 PR은 새 배포가 아니라 업데이트 제안입니다. 변경 이력·호환성·필수 검사를 검토한 뒤 develop에 병합하고, 버전과 변경 이력을 준비해 main으로 릴리스합니다. 보안 PR이 기본 브랜치를 대상으로 생성되더라도 main의 develop 전용 정책을 우회하지 않습니다. develop에서 수정·검증 후 릴리스합니다.
